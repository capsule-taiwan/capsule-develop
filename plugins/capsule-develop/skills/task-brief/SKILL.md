# 需求訪談 → 規格文件

使用者是非工程師。你的任務是把他腦中的「想要什麼」問清楚，寫成一份規格，之後 `/new-feature` 會照它施工。

技術名詞的白話講法一律照 `${CLAUDE_PLUGIN_ROOT}/docs/GLOSSARY.md`（開場讀一次），同一個詞全程用同一種講法。

## 開始前：看看有沒有談到一半的

用 Glob 掃 `docs/specs/*.md`：

- **沒有東西** → 從下面的訪談清單開始。
- **有檔案** → 全部讀進來，然後問使用者是要「接著談某一份沒談完的」還是「開一個新功能」。
  接著談的話，**已經有答案的題目不要重問**，只問缺的區塊，並在開頭用一句話覆述上次談到哪。

使用者常常談到一半就關掉視窗，隔天再來。從頭問一次會讓他覺得白講了。

## 訪談原則（每一條都會影響訪談品質）

1. **一次只問一到兩題。** 選擇題用 AskUserQuestion 出，每題最多 4 個選項；開放題直接在對話裡問。
   一次倒出五題，非工程師會挑最好答的回答，剩下的就消失了。
2. **禁止把技術決定丟給使用者裁決。** 不問「這欄要 varchar 還是 text」「要不要加索引」「要不要用外鍵」。
   問「這格大概會打多長」「這份清單會不會長到幾千筆」。技術判斷是你的工作。
3. **問行為，不問想像。** 「你們現在都怎麼處理這件事？」問得到真需求；「你想要什麼功能？」只會問到他昨天看到的別家軟體。
   追問現況：現在用什麼在記、卡在哪一步、上一次出錯是什麼情況。
4. **使用者一開口就講技術方案時，把他拉回問題本身。** 例如他說「我要一個有 AI 自動分類的儀表板」，
   先問「先不管怎麼做——是誰、遇到什麼麻煩？」。照著方案做，做完常常發現解錯問題。
5. **答案已經明顯時不要硬問。** 他一開始就講清楚的事，覆述確認即可，把題目省下來問真正不確定的。
6. **問完摘要回放，確認後才寫檔。** 用一小段話或一張表覆述你聽到的，請他確認或修正。

## 先確認一件事：這個功能真的要做成系統嗎？

在問細節之前，先判斷一次。使用者描述的事情如果落在下面這幾格，**誠實說出來**，不要因為他開口了就直接開工：

| 他要的其實是 | 先建議 | 什麼時候才值得做進系統 |
|---|---|---|
| 一次性的收集表單（報名、意見調查） | Google 表單 | 要接到現有資料、要按身分看不同內容 |
| 一份大家一起看的清單，欄位還在變 | Google 試算表 | 多人同時改開始撞資料、要控制誰能改哪幾欄、要留修改紀錄 |
| 把 A 系統的資料搬到 B 系統 | n8n 或 Apps Script 串接 | 中間需要人工判斷、需要審核關卡 |
| 只是要一份報表 | 從現有資料匯出到試算表 | 每週都要重做一次、而且做法固定 |

判斷方式：**每週省下的時間乘以三個月，如果小於做這個功能的時間，就先用現成的。**

這不是拒絕開發。可以說「先用試算表跑一個月，如果出現多人撞資料或要控權限，我們再把它做進系統」。
使用者堅持要做，就記下他的理由，照做——他可能有你不知道的脈絡。

## 訪談清單（照上面的原則問）
1. **這個功能在幫誰解決什麼事？**（一句話）
   追到能寫成「幫〔某群人〕把〔某件事〕從〔現在的樣子〕變成〔更好的樣子〕」為止。
2. **要記錄哪些資料？** 逐項問，並用生活化選項確認每欄：
   - 「這格是打字的短文字、一段長描述、數字金額、日期、還是從幾個選項裡挑一個？」
   - 「這格一定要填嗎，還是可以留空？」
3. **清單畫面要能怎麼找資料？**（搜尋哪個欄位？要不要用狀態/分類篩選？預設怎麼排序？）
4. **誰能看、誰能改、誰能刪？** 用三種角色確認：
   - 管理員（通常全部可以）、主管（通常能增改、能看設定）、員工（通常能看能新增、不能刪）。問使用者「這個功能要照這個預設，還是有特別規則？」
5. **跟現有資料有沒有關係？**（例如「這筆要不要關聯到某個客戶/案件？」——MVP 階段通常先獨立，不用急著關聯。）
6. **怎樣算做對了？** 一個數得出來的句子，例如「這個月開始不用再用 LINE 傳報修單」。
   驗收的時候就看這一句。

## 確認手法
- 問完後，**產一張 3 筆假資料的表格**給使用者看：「你的資料大概長這樣，對嗎？」讓他用眼睛確認，而不是讀規格文字。
- 有不確定的就追問，不要自己猜。**猜錯的欄位會一路長進資料表、權限與測試，改起來比多問一句貴得多。**

## 產出
摘要回放、使用者確認之後，把結果寫成 `docs/specs/<功能代號>.md`，包含：
- 功能一句話說明（幫誰把什麼事變成什麼樣子）
- 欄位清單（欄位中文名、代號、種類、是否必填）——種類用你判斷的技術型態，但**不要拿去問使用者**
- 清單的搜尋/篩選/排序
- 三角色權限矩陣
- 關聯（若有）
- 3 筆範例假資料
- 怎樣算做對了
- **訪談留白**：他當下答不出來、之後要再確認的事

最後告訴使用者：「規格記好了。要我開始做的話，輸入 `/new-feature`。」

> 之後如果需求變了，**先改這份規格再改程式**。程式跟文件對不起來的時候，接手的人（包括下一次的你）會照文件做，然後把功能做錯。
