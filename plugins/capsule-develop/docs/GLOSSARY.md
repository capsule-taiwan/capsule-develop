# 白話對照表（所有技能共用）

capsule-develop 的使用者是**非工程師**。每個技能都要求「用業務語言」，這張表就是那句話的具體內容：
技術名詞第一次出現時，用這裡的講法。

兩條原則：

1. **同一個詞全程用同一種講法。** 不要一下說「後端」一下說「伺服器端」，使用者會以為是兩個東西。
2. **表上沒有的詞，現場造一句同等白話的解釋**，並考慮補進這張表（開 issue 給平台團隊）。

## 一間店的比喻（貫穿全部說明）

| 技術名詞 | 白話講法 |
|----------|----------|
| 前端 | 使用者看得到、點得到的畫面，就像店面 |
| 後端 | 在背後處理事情、把關的那一層，就像廚房 |
| 資料庫 | 存放所有資料的地方，就像倉庫 |
| API | 前後場溝通用的固定格式，就像點餐單 |
| 部署／上線 | 把做好的東西放上網路，就像正式開店 |
| 雲端 | 租來的別人家電腦，機器壞了房東修 |

## 這個工具箱一定會用到的詞

| 技術名詞 | 白話講法 |
|----------|----------|
| 專案代號 | 這個工具的英文小寫名字，同時當資料表前綴、資料夾名、網址名 |
| repo | 程式碼保險箱：存程式碼的地方，兼歷史紀錄簿 |
| 版本控制 | 每次改動都留底，隨時可以回到之前的樣子 |
| commit | 存一次檔，附一句「這次改了什麼」 |
| push | 把本機存的檔推上 GitHub，別人和自動上線流程才看得到 |
| CI／自動上線 | 你一 push，GitHub 就自動幫你檢查並上線的流水線。**這個專案唯一的上線方式** |
| GitHub Actions | 跑那條流水線的地方；點進 repo 的 Actions 分頁就看得到每次上線是成功還失敗 |
| 回滾 | 出事時退回上一個正常版本 |
| migration（施工紀錄） | 每次改資料表結構都留一張有編號的施工單，能重演也能退回。**在 Supabase 網站上手點的設定視為不存在** |
| RLS（門禁規則） | 資料庫裡一列一列的規則，決定誰能看到、誰能改哪一筆資料 |
| 權限 | 誰能看什麼、改什麼；這個範本固定分管理員／主管／員工三種身分 |
| 金鑰（key／token） | 服務發給你的鑰匙，拿到就能動用你的帳號和錢 |
| 公開金鑰（anon key） | 設計成可以放進網頁的鑰匙，權限很低，安全靠門禁規則把關 |
| 秘密金鑰（service_role key） | 繞過所有門禁的萬能鑰匙，只能放在你自己的電腦，永遠不進程式碼 |
| access token | 你發給 Claude 代你操作某個服務的一次性通行證，用完自己留著 |
| 環境變數／`.env` | 放金鑰這類秘密的抽屜，跟程式碼分開收，不會進版控 |
| 登入／驗證 | 確認現在操作的人是誰 |
| OAuth（借櫃台登入） | 「用 Google 登入」這種做法，把驗身分交給 Google，我們拿不到你的密碼 |
| 本機／測試 | 只有你自己看得到的樣品屋，網址是 `localhost:3000` |
| 正式環境 | 有網址、同事都打得開的真店面，網址是 `<專案代號>.pages.dev` |
| 免費層／免費額度 | 服務免費送的用量，超過才收錢。內部工具幾乎用不完 |
| 託管 | 機器和維運都交給平台顧，你只管內容 |
| 備份 | 把資料多存一份在別的地方 |
| 還原 | 把備份拿出來，**真的變回原樣才算數**——沒還原過的備份不算備份 |
| 護欄（hooks） | 自動擋掉危險操作的安全網，被擋是刻意的，不要想繞過 |
| CLI | 用打字下指令的操作方式；Claude 會代打，你不用學 |
| context（工作桌） | Claude 一次能記住的對話量，桌子滿了就會開始忘東西 |
| 畢業回收 | 這個 MVP 成熟到值得收進公司母艦的流程，少數工具才會走到 |

## 怎麼用

- **訪談的時候**：只講白話欄的說法，技術名詞不要出現。不要拿技術決定去問使用者。
- **寫文件、寫報告的時候**：白話為主，技術名詞放括號附在後面，例如「資料庫（存資料的倉庫）」。
- **回報錯誤的時候**：先說「哪件事沒成功、對你的影響是什麼」，再說技術原因。
