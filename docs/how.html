!

第一次體驗不好，之後就沒人要用了

同事第一次打開你的工具，如果卡卡的、看不懂、資料是錯的，他就不會有第二次——而且他會跟別人說。所以第一版寧可只做一件事，但那件事要做到好用。

!

大家一開口都是完整版

問需求的時候，聽到的幾乎都是「汽車設計圖」——所有功能一次到位。你的工作是把它切開：這一版先做哪一塊？跟 Claude 說「先做最小可用版本」，它會幫你切。

!

腳踏車想升級機車，往往要重做

如果心裡的終點是汽車，第一版就要先講出來——不是先做出來，是先講。Claude 知道終點在哪，第一版的地基才不會蓋成之後得整個打掉。

!

終點真的是汽車的話，中間版本要不要做，先想清楚

「先做滑板車」不是萬用答案。如果這件事最後一定會長成汽車，做兩三台過渡的車可能反而是浪費。反過來說，「其實腳踏車就夠了」的案例並不多——多數需求最後還是會長到機車、汽車那一段。動工前花十分鐘把終點想清楚，比中途改三次划算。

02
兩條路

串接現成平台，還是做一個系統

這是兩條獨立的路，不是同一條路的前後段。先判斷你要走哪一條，會少走很多冤枉路。

路線 A · 01–03 號車

串接：n8n、Apps Script

不做新系統，把已經在用的工具接起來、讓流程自己跑。

  • Notion 新增項目 → 自動發 Slack 通知
  • 每週一早上自動彙總、寄出報表
  • 表單送出 → 寫進 Google Sheet → 通知負責人

什麼時候選它：資料本來就散在各平台、你要的是「自動接起來」而不是「一個新畫面」。做得最快。

路線 B · 04–05 號車

做系統：Web App（這個工具箱）

有自己的畫面、自己的資料庫、公司帳號登入與權限。

  • 要有人天天輸入、而且不能輸錯
  • 誰能看、誰能改、誰能刪要分得清楚
  • 要留紀錄：誰在什麼時候改了什麼

什麼時候選它：多人長期使用、資料要正確、權限要分。做得比較慢，但撐得住。

兩條路可以合作。常見的組合是：路線 B 做輸入的那一端（要嚴謹），路線 A 負責把結果送到大家已經在用的地方（Slack、Sheet、信箱）。下一段講這個組合怎麼配。
03
接 Google Sheet

跟 Google Sheet 串接：規定一條，建議一條

很多工具最後都會需要跟 Sheet 來往。這裡只有一條硬規定，其餘都是建議，你可以自己判斷。

硬規定：一律走 service account，而且帳號一律由工程師產出。不要用自己的 Google 帳號授權，也不要自己去 Google Cloud 開一組。跟 IT 說你要接哪一份 Sheet、要讀還是要寫，他們會給你一組 service account 與設定方式。

為什麼一定要這樣

→

不會綁在某個人身上

用個人帳號授權的話，那個人離職、換職位、或哪天把權限收回來，你的工具就在沒有人預期的時候壞掉。service account 是一個獨立的機器帳號，不隨人走。

→

權限給得剛剛好，也收得回來

service account 只被分享到「它該碰的那幾份 Sheet」，不像個人帳號一授權就是整個雲端硬碟。要停用也只要撤掉一組帳號，不影響任何人。

→

看得出是誰動的

Sheet 的編輯紀錄會顯示是那個 service account 寫的，跟人的操作分得開。出事的時候查得到，不會變成「不知道是誰改的」。

建議（不是規定）：輸入端做在系統，輸出端做在 Sheet

輸入端 → 做在系統

因為輸入需要「管得住」：

  • 擋得住錯的：日期就只能填日期、金額不能是負的、必填就是必填。Sheet 裡誰都能打任何東西進去。
  • 選項統一：下拉選單選部門，不會出現「業務部／業務/業務處」三種寫法，之後統計才對得起來。
  • 留得下紀錄：誰在什麼時候改了什麼，系統自己記。Sheet 的版本紀錄很難查、也容易被覆蓋。
  • 分得了權限：有人只能填自己的、主管才能看全部。Sheet 一旦分享出去，通常就是整份都看得到。
  • 不怕手滑：Sheet 常見的災難是有人排序時只選了一欄，整份資料錯位，而且沒人發現。

輸出端 → 做在 Sheet

因為看資料需要「夠靈活」：

  • 大家本來就會用：不用教，打開就會篩選、排序、拉樞紐分析。
  • 你不用寫報表：主管想換個角度看，他自己拉就好，不用回頭找你改程式。
  • 接得上既有工作：複製進簡報、丟給會計、餵進別的表，都是現成的。
  • 要什麼圖自己畫：圖表、條件式格式都是內建的，比你自己刻快太多。
一句話記法：要寫進去的，走系統；要拿出來看的，走 Sheet。這只是建議——如果你的情境反過來比較順（例如資料本來就長在 Sheet、只是要一個好看的檢視畫面），那就反過來做，沒問題。

幾個實際的配法

情境輸入端（系統）輸出端（Sheet）
排班 同事填意願、設定班別規則；系統擋掉衝突與超時 排好的班表寫回 Sheet，大家用手機打開就看得到，也能直接印
驗收 / 收款追蹤 案件狀態在系統更新，誰改的有紀錄 每天把當日異動與未結案清單寫進 Sheet，會計自己拉樞紐對帳
庫存 / 資產 進出貨在系統登記，有權限、有品項下拉 每晚把庫存快照寫進 Sheet，主管看趨勢、做採購決策
問卷 / 申請單 表單在系統，必填與格式檢查都做在這 結果同步到 Sheet，讓各單位自己篩自己要的那幾列
04
用真實資料測

請用真實的資料、真實的流程去測

用假資料測，只能測出「程式沒壞」；要測出「這東西真的能用」，就得用真的東西餵它。

→

假資料永遠很乖

你自己編的資料不會有全形空白、不會有備註欄塞了兩百字、不會有同一家客戶三種寫法、不會有金額是零或負的。真實資料全都有，而且第一天就會出現。

→

真實流程才有例外

「請假到一半取消」「同一天改三次」「主管不在要代簽」——這些只有真的跑一遍才會冒出來。假流程一路順暢，上線第一週就會被真實情況打臉。

→

早點給人用，比做完再給好

找一兩個願意幫忙的同事，用他手上真的在跑的案子試一次。這一次得到的回饋，比你自己想三天還準。不用等到完美——但要先講清楚「這還在測試」。

還是要注意的兩件事：特別敏感的資料——薪資、個人身分資料、客戶合約金額這一類——動之前先問 IT 一聲，他們會告訴你要不要先把專案搬到公司帳號底下。另外，測試期間要刪資料、重跑流程之前，先確認那份資料在別的地方還有一份。
05
五個名詞

模型、Agent、API、MCP、Skill

這五個詞你之後一定會聽到。用同一個廚房的比喻講一遍，就不會再混淆了。

模型Model
＝ 廚師的腦袋會的菜、懂的原理、判斷力。模型本身只會「想」跟「回答」，不會自己動手。在 Claude Code 裡換模型，就是換一顆腦袋——有的想得深但慢，有的反應快但淺。
AgentAgent
＝ 會自己動手的廚師本人腦袋加上手腳。它會自己打開檔案、寫東西、執行指令、看結果不對再改。你用的 Claude Code 就是 Agent——這就是為什麼它能真的把專案做出來，而不只是給你一段程式碼要你自己貼。
APIAPI
＝ 出餐窗口兩個軟體之間講話的窗口，有固定格式：你按規定遞單子進去，它按規定把東西遞出來。你的工具跟資料庫要資料、跟 Google Sheet 寫一列進去，走的都是 API。
MCPModel Context Protocol
＝ 萬用轉接頭讓 Claude 能接上外面的服務——Slack、Notion、Google Drive、公司自己的系統。接上之後，你可以直接叫它「去看那份 Notion 文件」「把結果貼到 Slack」。沒接就沒有。
SkillSkill
＝ 寫好的食譜把一件事的標準步驟寫下來，之後每次都照著做、結果都一樣。你打的 /new-project、/check 就是 skill——不是模型臨場發揮，是有人先把流程寫好了。這個工具箱本身就是一包 skill。
06
模型與思考深度

什麼時候該換腦袋、什麼時候該讓它想久一點

兩個可以自己調的旋鈕。多數時候維持預設就好，但卡關的時候知道有這兩個旋鈕，會省下很多來回。

旋鈕怎麼調什麼時候調
換模型model /model 換一顆腦袋。強的模型理解複雜需求、處理棘手 bug 比較穩，但比較慢也比較貴；快的模型適合改字、調版面這種明確的小事。
思考深度effort /effort 同一顆腦袋，讓它想久一點再動手。需求很模糊、或它連續改了兩三次都沒改對的時候，調高通常有用。
不是越高越好。想得越久＝越慢、越貴。日常「照著做」的事情用預設最划算；真正值得調高的時機是：需求很模糊、它連續改錯、或這個決定之後很難回頭（例如資料表怎麼設計）。
07
組成

你的工具是由哪幾塊組成的

你會聽到一堆名字。其實就是開一家店會用到的幾樣東西，一個一個對起來就懂了。

你會聽到相當於它在做什麼
Claude Code幫你做事的師傅你講需求、它動手做。整套流程都在它裡面跑。
VS Code或終端機工作檯師傅工作的地方。VS Code 是「有畫面」的工作檯，終端機是「只有文字」的——兩個做的事完全一樣，看你習慣哪個。
git / GitHub存檔點與雲端備份每做完一段就存一個檔，改壞了可以退回去。GitHub 是把這些存檔放到雲端，換一台電腦也拿得到。
Supabase倉庫 ＋ 門禁資料存在這裡，誰能進來、誰能看哪些也是它在管。免費。
Cloudflare Pages店面地址給你一個網址，同事用瀏覽器就打得開。免費。
Node.js工作檯的電源很多開發工具要靠它才能跑。裝一次就好，之後你不會再碰到它。
這六樣裡面，你真正要自己動手的只有兩件事：去 Supabase 註冊一個免費專案、去 Cloudflare 拿一把鑰匙。其餘全部由 Claude 代勞，它會在需要你出手的時候停下來告訴你。
08
前端與後端

「前端」「後端」，以及你的工具做得到什麼

這兩個詞會一直出現。一句話講完，你就知道自己的工具能做到哪、哪些要找幫手。

前端 ＝ 你看得到、點得到的畫面

跑在使用者自己的瀏覽器裡：頁面、按鈕、表單、清單。使用者直接看到、直接操作的都是。

後端 ＝ 在雲端幫你跑事情、把關的那一層

使用者看不到也改不了：存資料、驗身分、照時間自動做事、保管祕密鑰匙。它在雲端 24 小時待命。

做得到 —— 大多數內部工具

  • 記錄、清單、搜尋、篩選、分頁
  • 新增／編輯／刪除資料
  • 公司 Google 帳號登入
  • 權限控管：誰能看、誰能改、誰能刪
  • 報表畫面、簡單的統計

做不到 —— 要「真正的後端」才好做

  • 定時自動執行：每天早上自動寄週報、到期自動提醒。
  • 要藏密鑰的串接：接金流、寄 email、呼叫別家服務。密鑰不能放在畫面裡。
  • 大量背景運算：批次匯入匯出、處理圖片。
右邊那些怎麼辦？大多數情況交給路線 A（n8n / Apps Script）就解決了——定時、通知、把資料送到 Sheet，本來就是它的強項。這也是為什麼兩條路常常一起用。真的需要公司級的正式功能，再找 IT。
09
常見問題

你可能會想問

我完全不會寫程式，真的可以嗎？

可以。你要會的是「把你想要什麼講清楚」，這件事你比工程師強。程式由 Claude 寫、由它檢查，它還會用白話告訴你怎麼在畫面上驗收。你看不懂的東西不用假裝看得懂——直接問它「這在做什麼」。

我做的工具最後都會被收進公司大系統嗎？

不會，而且不需要。大部分工具會一直是它自己——一個專門解決某個小問題、被固定幾個人用得很順的東西，這樣就很有價值了。「畢業收進母艦」是少數情況：用的人變很多、變成公司關鍵流程、或需要跟其他系統深度整合的時候，才值得走那一步。不要為了畢業而做，做出好用的東西就好。

要花錢嗎？

你會用到的服務都在免費額度內（Supabase、Cloudflare 的免費方案，內部工具綽綽有餘）。要付費的是 Claude Code 本身，那個公司出。

會不會弄壞公司的系統？

碰不到。你的工具用的是你自己的資料庫和網址，跟公司正式系統完全分開。工具箱裝好後還會自動啟動幾道護欄，擋掉危險操作——例如不小心要刪掉工作成果、或動到公司正式機的設定，它會直接擋下來並告訴你原因。

我可以自己決定要怎麼做嗎？

可以，而且鼓勵。除了兩件事是硬規定——接 Google Sheet 一律走工程師給你的 service account、不改平台共用區——其餘都由你判斷：畫面怎麼排、流程怎麼走、要不要拆成兩個工具、先做哪一塊。這頁寫的大多是建議，不是規則。做出來覺得不順，改掉就好。

做到一半卡住怎麼辦？

直接跟 Claude 說「我卡住了」，把畫面上看到的貼給它。真的需要人幫忙的時候（開通登入、要 service account、接第三方服務），它會告訴你去找 IT——那不是你做錯了，是那幾件事本來就需要權限。
